# 研究切口与实验路线

核心判断：第一篇论文应聚焦“frozen VLA harness 中跨任务共享 skill implementation 的受验证修复”，并把 `allow_code_edit` 相对 plan/memory-only recovery 的增量效应隔离出来；宽泛的 robot program repair 已不足以形成独立切口。

## 推荐题目

英文：

> Beyond Fixed Harnesses: Verifier-Guided Program Repair for Embodied Robot Skills

中文：

> 超越固定 Harness：面向机器人技能的执行反馈程序修复与外部验证

## 研究问题

在冻结 RPent/Harness VLA 的 planner、VLA、初始 memory、感知栈、部署预算与外部 evaluator 后，允许 agent 只修改受限 skill workspace，能否在预注册的 code-repairable failure families 上超过 compute-matched 的 plan/memory-only baseline，并满足 final-blind generalization、regression 与 safety 门？

这里的统计单位、推翻条件与暂定 margin 以 [[问题定义与实验假设]] 为唯一规范；本页只维护工程执行顺序。

## 与直接近邻的区别

[[Harness VLA]] 已经证明，冻结 VLA 配合固定 primitive、task-specific trace memory、planner re-grounding 和局部 retry，可以在扰动 benchmark 上大幅提升。它是本项目现在必须正面对比的直接近邻。

因此，第一篇论文不能只证明“agent + memory + primitives 比端到端 VLA 更好”。它必须进一步证明：

> 在控制 planner、memory、retry budget 和 VLA backend 后，允许 agent 修改并验证 skill/harness 的受限实现，能否修复 fixed harness 仍然失败的 held-out cases，并保持旧任务无回归？

[ASPIRE](https://arxiv.org/abs/2607.00272) 已经覆盖 per-primitive trace、robot program repair、closed-loop validation、skill guidance library 与 evolutionary search。因此我们的修复对象必须是**跨任务共享、已有版本的 implementation**，而不是每个任务新生成的 program 或 in-context guidance。

[VASO](https://arxiv.org/abs/2606.05395) 已经覆盖 formal verifier-guided semantic skill contract evolution。因此我们必须明确当前 verifier 的贡献是 empirical Robot CI：hidden target tests、跨任务 regression、safety 和 rollback；formal contract 是可组合门，而不是尚未有人做过的主张。

## Codebase 决策

[RPent](https://github.com/RLinf/RPent) 是框架/codebase，Harness VLA 是它的首个论文系统和 fixed-harness 配置。因此可以用 RPent 开发本项目，同时把 Harness VLA 保留为同一框架中的冻结 baseline mode。但截至 2026-07-29，RPent 仍是 `0.0.0` / pre-alpha，完整公开路径主要限于 Pi0.5 + LIBERO-Pro，并存在许可证、rolling memory 与论文 artifact 未完全冻结的问题。

因此当前决定是：

- **Baseline：GO**。冻结一份 Harness VLA-style fixed harness，作为必须击败的直接对照。
- **Codebase：Conditional GO**。先做 3–5 天 LIBERO-Pro spike；许可证、完整冻结、mini replication 与 defect-repair probe 全部通过后，再决定是否长期采用。
- **实现结构**：在同一 RPent codebase 中保持 frozen `fixed_harness` 与 `code_evolving` 两种模式，避免方法修改反向污染 baseline。

完整证据、风险和 Go/No-Go 门见 [[Harness VLA采用决策]]。

## 从官方 RPent baseline 开始

核心判断：先把 [RPent](https://github.com/RLinf/RPent) 当作冻结实验底座，完成“可复现 baseline -> 单 primitive repair -> postcondition repair -> 端到端验证”四级闸门；不要一开始让 coding agent 修改整个 planner、memory 或 VLA 路径。

### Gate 0：复现官方最短路径

官方当前最完整的路径是 Linux/CUDA 上的 LIBERO-Pro、Pi0.5 与 SAM3。第一步只做一个官方任务的烟测：

```bash
git clone https://github.com/RLinf/RPent rpent
cd rpent
git rev-parse HEAD  # 保存为 baseline manifest
pip install -e ".[full]"
liberopro-download-assets --skip-existing

rpent --env libero --suite libero_object_swap --task 2 --seed 0 \
  --planner codex --model <固定模型版本> --dashboard
```

若使用其他 planner，必须从第一次实验起固定 backend、model 版本、prompt、turn/token budget。这个 smoke run 的验收条件不是达到论文均值，而是：三个服务健康、任务能完整结束、`transcript`、`states`、`recipe` 与视频均可读取。随后用完全相同配置跑同一任务的 3–5 个 held-out seeds，先测量底座本身的方差。

在进入 code repair 前，可做一次小型 baseline audit：把 memory 条件固定为 `none / global-only / task-only / both`，比较相同 seeds 下的成功率、VLA calls、env steps 和 planner tokens，并把实际读取的 memory 文件与 hash 写入 transcript。它用于确认 Harness VLA 收益来自哪里，但不应被包装成本项目的主要创新。

**环境推断**：官方只承诺 Linux；Windows 主机若走 WSL2，必须先单独通过 CUDA、EGL/MuJoCo 渲染和完整 episode 烟测，不能默认等同于受支持的 Linux 环境。官方没有给出最低显存承诺，因此显存是否足够也应作为 Gate 0 的实测结果，而不是预设。

### Gate 1：先修一个解析 primitive

第一条 repair 闭环优先选择 `rotate_wrist` 或 `move_to`，不要直接动 VLA。先扫描成功 `recipe_*.jsonl`，选择确实在目标任务中被调用的 primitive，避免修复一个端到端 rollout 根本不用的组件：

1. 从官方 primitive 外再包一层小型、可编辑 adapter，不让 agent 直接改整个 `robots/libero/tools.py`。
2. 注入一个因果明确的缺陷，例如坐标系/旋转符号、action scale 或缺失 timeout fallback。
3. 固定 primitive recipe，先绕开 planner 的补偿能力；trace 至少记录 `start`、`target`、`final`、`error`、步数和 termination cause。
4. repair agent 只能修改 adapter 与 held-in tests，最多生成固定次数的 patch proposal。
5. verifier 依次运行静态检查、primitive contract、hidden regression、安全约束和回滚检查。

这一步只验证 repair plumbing：失败 trace 是否足以支持正确归因，patch 是否能通过不可编辑 evaluator，以及系统是否能拒绝放宽预算、阈值或安全边界的“伪修复”。若注入的缺陷来自官方历史 bug，必须把可编辑模块、注释和 git history 做匿名化/清洗，否则 agent 可能直接读到修复答案。

### Gate 2：再修 `pi0_pick` 的 postcondition

[RPent 当前实现](https://github.com/RLinf/RPent/blob/main/robots/libero/tools.py)已经为 `pi0_pick` 返回 descent、post-descent ascent、gripper opening、chunk budget 与 `libero_terminated` 等诊断字段。因此第二个实验可以只开放 early-return/postcondition detector，保持 Pi0.5 权重与 `vla_server` 冻结：

- 注入或采样 empty-grasp false positive、厚物体 false negative、过早结束等 monitor 缺陷。
- verifier 可以用仿真器 oracle 状态生成 detector label，但这些 privileged 字段不能进入 planner 或 repair agent 上下文。
- patch 的目标不是直接提高 detector 分数，而是让正确的失败返回触发 re-stage/retry，并在等预算 held-out episode 上提高官方 completion predicate。

这会形成一条更有说服力的因果链：`monitor code patch -> primitive 返回变化 -> planner recovery 变化 -> task success 变化`。

### Gate 3：端到端等预算验证

当 primitive contract 与 detector evaluator 都稳定后，再恢复完整 planner，让同一 accepted patch 在 held-out episode 中运行。必须同时做三项检查：成功 rollout 确实调用了被修改组件；移除该 patch 的 ablation 会让收益消失；repair 与 fixed harness 的 VLA calls、env steps、retry、LLM tokens 和 wall-time budget 保持相同或单独报告。只有通过这一步，才能把结果称为 harness code repair 的收益。

### 必须冻结与允许编辑的边界

| 类别 | Gate 1–2 的处理 |
| --- | --- |
| VLA 权重、`vla_server`、planner/model/prompt | 只读并固定版本 |
| Task/Global Memory、primitive vocabulary/schema | 只读，避免与 code repair 混淆 |
| retry、VLA call、env step、turn/token/time budget | 各条件严格相同，不允许 patch 放宽 |
| LIBERO 资产、physics、seed split、官方 scorer | 只读并写入 manifest |
| raw trace、hidden tests、verifier、安全 clamp | 对 repair agent 不可见或只读 |
| 单个 analytic adapter 或 postcondition detector | allowlist 内可编辑 |
| tests | 只允许新增 held-in test；hidden/clean regression 不可编辑 |

首轮至少比较四个等预算条件：fixed broken harness、retry/replan only、repair + verifier、human/oracle patch 上界。Direct frozen VLA 可保留为 sanity baseline，但验证 code repair 新意的核心对照是 fixed harness 与 repair harness。

### 两周 go/no-go 标准

第一轮不追求论文级总体分数，而追求闭环可信度：

- 官方 seed 0 和 3–5 个 held-out seeds 可重复运行，记录完整 manifest 与 trace。
- 至少构造 3 个可归因缺陷，repair loop 修复其中 2 个以上。
- clean no-fault regression 不出现明显下降，安全违规为 0。
- 至少一个 end-to-end 成功能够被同一 patch 的 ablation 消除，证明 planner 实际使用并受益于修改后的组件。
- 收益不能由增加 `max_chunks`、重试次数、环境步数或 LLM 预算解释。

若这些条件未通过，下一步应优先改 trace schema 与 evaluator，而不是扩大可编辑范围或切换到 RoboCasa/真实机器人。

## 最小可行系统

第一阶段只做 3 个基础模块：

1. Skill registry：记录 skill 的输入、输出、precondition、postcondition、安全约束、测试。
2. Trace collector：记录失败时的关键状态和多模态证据。
3. Repair loop：coding agent 生成 patch，verifier 运行测试，失败则回传结果。

这些模块是验证研究问题所需的基础设施，不单独作为 novelty。不要一开始做完整自然语言家庭管家；任务大脑可以先很简单，甚至由脚本固定调用 skill。

## 实验任务

采用 spike 和 pilot 先限于 4 个 LIBERO-Pro tasks。主集合的 deliberate defects 覆盖：

- perception/geometry interface：frame、unit、depth validity、坐标变换；
- primitive/contract：参数传递、gripper state、局部控制 contract；
- local monitor/postcondition：stale state、early return、局部 false positive/negative；
- exception/fallback/FSM：IK/执行错误分支与状态转移。

原始 perception model 无识别能力通常属于 policy/perception-limited；只有 perception API 使用、过滤或坐标接口错误才属于 code-repairable。外部 success evaluator 错误属于 trusted-kernel negative control，不能让 agent 修改；可编辑的只是 skill 内部局部 postcondition/monitor。

## 实验流程

```text
1. 运行初始 skill，收集失败 trace。
2. coding agent 做 failure attribution。
3. agent 生成 patch proposal 和新增测试。
4. verifier 运行 unit/sim/regression/safety tests。
5. 如果失败，把测试输出回传 agent。
6. 如果通过，部署到下一批 held-out 场景。
7. 记录成功率、修复轮数、regression 和安全违规。
```

## Baseline

从相同 frozen artifact 与 failure traces 出发，运行：

1. Frozen Harness：不做持久适应；
2. Plan/memory only：代码只读，允许 Harness VLA 的 memory、re-grounding、staging 和 retry；这是 primary baseline；
3. Code only：只允许 gated `ΔW`；
4. Plan/memory + gated code：ours/full；
5. Full without gate：相同候选 pool 的 verifier ablation；
6. Clean reference 与 human/oracle patch：性能上界和 failure adjudication。

这构成 `Δmemory × Δcode` 的近似 2×2 设计。Direct VLA、ASPIRE-style task-program generation、learned-policy update 与参数搜索只作为背景、边界或 defect-specific baseline；不能替代 primary comparison。

## 指标

核心指标：

- final-blind held-out success 与 normalized recovery；
- 相对 plan/memory-only 的 paired gain；
- safe-repair rate：目标收益达标、regression 合格且无 severe safety violation 的 defect 比例；
- unaffected-task regression 与 5 pp non-inferiority；
- severe/minor safety violation、false acceptance 与 rollback；
- adaptation/deployment 两类预算下的 tokens、probes、VLA calls、wall-clock 与成本。

辅助指标：

- failure attribution 准确率。
- 新增测试是否覆盖真实失败。
- patch 大小和复杂度。
- 是否产生不可解释或绕过安全门的代码。
- harness-updating 成功率：proposal 是否正确修改目标组件并通过局部 evaluator。
- harness-benefit：完整 planner 是否在 held-out task 中实际调用并受益于新 skill/tool。

## 里程碑

### Milestone 0：RPent 采用 Spike

先固定 RPent commit、VLA checkpoint、RPent-memory revision、planner/prompt 和全部预算，在 4 个 LIBERO-Pro tasks 上做 direct VLA、no-task-memory harness 与 full fixed harness 的 mini replication；再加入一个故意有缺陷的 primitive，验证外部 verifier、held-out regression 和 rollback 能否在不修改 trusted core 的前提下接入。具体门槛见 [[Harness VLA采用决策]]。

### Milestone 1：纯仿真 proof-of-concept

运行 6-case LIBERO-Pro pilot：4 个 code-repairable defects、1 个 plan/memory negative control、1 个 policy-limited control，覆盖 4 个 tasks；每 case 给 2 条 repair traces、评估 5 个 final-blind seeds，并做 3 个 repair-agent seeds。Go 条件见 [[问题定义与实验假设]]。

### Milestone 2：回归测试和 skill library

为共享 skill 建 hidden target/regression/safety suite，用 mutation variants 检查测试强度；完成版本、回滚和冻结 manifest。

### Milestone 3：真实机械臂小样本验证

选择 Franka、UR5、xArm、ALOHA 或 LeRobot 风格平台，在低速低力设置下验证 2 到 3 个 skill。

### Milestone 4：论文级 benchmark

使用与 pilot 完全隔离的 tasks/defects，扩展到至少 12 个 code defects、多个 negative controls、每单元至少 10 个 final-blind seeds 和多个 repair-agent seeds；再按 pilot 方差做 power analysis。发布 fresh mutant snapshots、failure traces 与外部 evaluator。

## 最小论文贡献

1. 最小充分干预 taxonomy 与 plan/code/policy/trusted-kernel routing。
2. 同一 hybrid VLA harness 上隔离 `allow_code_edit` 的因子实验。
3. 跨任务共享 implementation 的 deliberate + natural defect repair benchmark。
4. mutation-strengthened、只读的 Robot CI/CD verifier、safety gate 与 rollback。
5. final-blind、按 defect family 聚类且预算匹配的实证结果。

## 下一步阅读优先级

4. [STING](https://arxiv.org/abs/2604.01518) 与 [vla-eval](https://arxiv.org/abs/2603.13966)：设计足够强、可冻结和可复现的 hidden evaluation。
