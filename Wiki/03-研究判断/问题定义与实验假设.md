# 问题定义与实验假设

核心判断：第一阶段论文不应检验笼统的“自进化能否提高机器人成功率”，而应检验一个受限、可证伪的问题：当 RPent/[[Harness VLA]] 已经穷尽规划、memory、re-grounding、重新 staging 和 retry 后，受验证的局部 skill code patch 是否还能在未见场景产生额外收益，并且不增加回归和安全风险。

状态：实验设计 v0.1，2026-07-29。数值门槛是 pilot 前的暂定值；只能用与正式检验完全隔离的 pilot set 校准一次，随后预注册并冻结。

## 推荐研究定位

暂定英文题目：

> Beyond Fixed Harnesses: Verifier-Guided Program Repair for Embodied Robot Skills

中文：

> 超越固定 Harness：面向机器人技能的执行反馈程序修复与外部验证

第一篇论文应把 “self-evolution” 落到 **verifier-guided program repair**，而不是一开始主张开放式 lifelong skill discovery。先证明一次局部修复真实、可泛化、无回归，后续才能讨论多轮积累。

## 2026-07 Novelty 审计

两篇新工作使“机器人根据执行反馈修代码并积累 skill”本身不再足以构成新意：

- [ASPIRE](https://arxiv.org/abs/2607.00272) 已经在 code-as-policy 系统中提供 per-primitive multimodal traces，让 coding agent 诊断失败、改写并验证 task program，再把有效修复压缩为可检索的 skill guidance，并用 evolutionary search 扩展候选程序。其 debug/evaluation seeds 也是分离的。
- [VASO](https://arxiv.org/abs/2606.05395) 已经把 verifier counterexample 反馈给可复用 semantic skill contract，在冻结 foundation model 权重的情况下做 verification-guided self-evolution；它验证的是 LTL temporal contract，实验对象主要是地面机器人与无人机规划。

因此本项目不能把以下内容单独写成贡献：execution trace、coding agent repair、验证后入库、冻结模型权重，或“self-evolving skill”这个宽泛叙事。更可辩护的差异化范围是：

1. **修复对象不同**：修复 RPent/Harness VLA 中跨任务共享的、已有版本的 skill/primitive implementation，而不是每个任务重新生成的 program、in-context repair guidance 或 semantic planning contract。
2. **系统边界不同**：把 VLA 作为冻结的低层 contact primitive，研究 hybrid harness 何时应该改 plan/memory、何时应该改 wrapper/skill code、何时必须承认 policy limitation。
3. **因果对照不同**：用 `Δmemory × Δcode` 因子设计，在相同 planner、VLA、trace 和双预算下隔离“允许改代码”的增量效应。
4. **验收标准不同**：外部 Robot CI 不只验证目标任务，而要用 hidden、跨任务的 regression/safety suite 决定共享实现能否部署和回滚。

以上仍是**研究定位与 novelty 假设**，不是完整查新后的事实结论。ASPIRE 必须进入最优先精读和论文级 related-work 对照；如果后续发现它已经覆盖共享 implementation repair 与跨任务 regression，本项目还需继续收窄。更广的路线对照见 [[相关工作地图]]。

## 主研究问题

> 在固定 RPent commit、execution planner、VLA 权重、初始 memory、感知栈、任务分布、部署预算和外部 evaluator 的条件下，给 coding agent 少量失败 execution traces，并只允许它修改预先声明的 skill workspace，它能否比 compute-matched、代码只读的 Harness VLA 更有效地修复 code-repairable failures，在 hidden held-out 场景保持收益，同时满足 regression 与 safety gate？

这个问题刻意不问：

- coding agent 能否通过增加 rollout、retry 或 token 获得更高成功率；
- planner 能否写出更好的 task memory；
- VLA 微调是否能学到新接触能力；
- agent 能否修改 success evaluator 后让分数变高。

这些都是不同处理变量，必须另做实验。

RPent/Harness VLA 的具体冻结项、许可证风险、evaluator 复核与 Go/No-Go 门见 [[Harness VLA采用决策]]。

第一阶段主实验以“失败已经被检测，并提供预注册格式的 trace”为条件，测的是 **conditional repair quality**。[SAFE](https://arxiv.org/abs/2506.09937)-style failure trigger 属于独立 monitor 问题；若把它接入端到端系统，必须另外报告 detection recall/precision、检测时延和未触发修复的失败，不能把完美 failure oracle 免费计入本方法。

## 形式化定义

沿用 [[机器人Harness工程]] 的边界，把 RPent 系统写成：

```text
S = (K, P, W)
```

- `K`：只读可信内核，包括模型身份与权重、execution planner 代码和 prompt、memory 机制与初始 snapshot、环境、外部 evaluator、隐藏测试、预算、权限和安全限制。
- `P`：可持久化的非代码状态，包括 task trace、plan skeleton 和有来源的 memory rule。最强 fixed-harness baseline 可以更新 `P`。
- `W`：受限可编辑 skill workspace，包括指定 primitive 的实现、局部参数、pre/postcondition、异常处理、fallback/FSM 和公开测试。

repair agent 获得 held-in failure traces `D_repair`、`W`、API 文档和公开测试，输出 patch `ΔW`。外部 gate `G` 决定是否接受；其分层门禁与回滚原则见 [[Robot CI-CD与安全门]]。最终目标是：

```text
maximize   held_out_success(K, P', W + ΔW)
subject to regression_drop <= ε
           severe_safety_violations = 0
           ΔW does not modify K
           adaptation/deployment budgets are respected
```

第一阶段不允许任意新增 primitive、不允许更新 VLA 权重，也不允许编辑全局 planner、evaluator 或 safety kernel。先把单个现有 skill 的 program repair 做干净。

## 失败类型：按“最小充分干预”定义

失败类型不是由终局错误码决定，也不是一个场景的永久属性；它相对于当前 editable surface 和可用 intervention 定义。

| 类型 | 操作化定义 | 期望系统行为 | 例子 |
| --- | --- | --- | --- |
| Plan/memory-repairable | 固定代码时，oracle plan/memory 仅靠重绑定、顺序、参数、staging 或 retry 就能在审计 seeds 稳健恢复 | 更新 `P`，不改 `W` | 选错目标、起始 staging 不当、primitive 顺序错误 |
| Code-repairable | oracle plan/memory 仍失败；但不改 VLA、planner、evaluator 和安全内核时，一个受限最小 patch 能恢复 | 归因到组件，修改 `W`，通过 gate | 坐标变换错误、局部 threshold、错误 postcondition、异常处理或 FSM 转移 |
| Policy-limited | planner 和 wrapper 正确，在多组有效 staging state 上当前 VLA primitive 仍失败；只有替换、微调或训练低层 policy 才恢复 | 拒绝伪修复，建议训练/替换 policy | 冻结 VLA 不会某类精细插入或新接触模式 |
| Trusted-kernel / out-of-scope | evaluator、仿真器、传感器、硬件、任务可行性或证据本身有问题 | abstain、上报，不编辑受保护组件 | success/truncation 聚合错误、传感器丢失、目标物理不可达 |

预注册的判定顺序：

1. 原代码 + oracle plan/memory 能否恢复？能则属于 plan/memory。
2. 如果不能，允许范围内的已知 oracle patch 能否恢复？能则属于 code。
3. 如果仍不能，oracle/更强低层 policy 能否恢复？能才属于 policy。
4. 否则归为 unknown/out-of-scope，不能因为“没找到 patch”就宣布 policy-limited。

分类使用的 adjudication seeds 与最终 evaluation seeds 必须分离。对于 deliberate defect，干净实现和隐藏 oracle patch 提供反事实证据；自然失败只能在冻结 taxonomy 后作为外部有效性实验。

## 实验假设

### H1-P：代码修复的增量效应（Primary）

在预注册的 code-repairable failure families 上，`code_evolving` 相比最强的 plan/memory-only Harness VLA，在 compute-matched 条件下提高 held-out success，同时满足：

- 暂定实际意义门槛：目标成功率绝对增益至少 10–15 个百分点；
- regression suite 成功率下降不超过 5 个百分点；
- 不新增 severe safety violation；
- success、failure、timeout 与 truncation 由不可编辑 evaluator 独立判断。

推翻条件：

- paired held-out gain 的置信区间没有超过预注册门槛；
- 收益在匹配环境交互、VLA calls、tokens 或 wall-clock 后消失；
- 收益只出现在触发修复的 held-in traces；
- 回归或安全门不满足；
- patch 触碰 `K`，或通过放宽预算/evaluator 获胜。

### H2：机制特异性与选择性

预期存在 `allow_code_edit × failure_type` 交互：

- 在 code-repairable 集合上，代码编辑产生增量收益；
- 在 plan/memory 集合上，强 fixed-harness baseline 应基本追平；
- 在 policy-limited 与 trusted-kernel 集合上，系统应 abstain 或正确升级处理，而不是制造“万能 patch”。

推翻条件：主要收益来自 plan/memory failures，或者 agent 频繁编辑错误模块、protected component 与真正的 policy limitation。

### H3：修复能泛化，而不是拟合失败 trace

patch 应在没有参与生成 patch、gate 或反馈的新 seed、对象位置、对象实例和调用同一 skill 的其他任务上保持正收益。

指标：

- held-in 与 final held-out success；
- `generalization ratio = held-out gain / held-in gain`；
- 跨任务的同-skill transfer；
- seed-specific 坐标、对象 ID 和 evaluator loophole 比例。

暂定要求 `generalization ratio >= 0.5`；正式门槛由独立 pilot 校准后预注册。

### H4：外部 Verifier 提高安全修复质量

相对相同候选 patch pool 的 ungated code editing，verifier-gated repair 应：

- 降低 false acceptance；
- 降低 hidden regression 与 safety violation；
- 保留大部分有效 target gain；
- 提高 safe-repair rate，而不只是拒绝所有 patch。

推翻条件：有无 gate 结果相同，或 gate 大量接受 harmful patch / 拒绝 correct patch。

### H5：结构化 Trace 与 Failure Attribution 是有效机制

相比只给 terminal outcome、最终图像和自由文本 transcript，带 primitive version、前后状态、错误码、轨迹、postcondition 理由和 component map 的结构化 trace 应提高：

- failure-type macro-F1；
- target-component top-1 accuracy；
- safe-repair rate；
- 单次成功修复所需的 proposal 数、tokens 和环境 probes。

推翻条件：trace ablation 不降低修复率，或 attribution 正确性与 patch 成功无关联。

### 后续假设：软件资产能否摊销

“一次 patch 在后续多个 episode 降低 retry、VLA calls、tokens 与成本”很重要，但不应成为第一轮 confirmatory experiment 的主假设。等单次 repair 成立后，再做 sequential/lifelong experiment，测 break-even 使用次数和累计 regression。

## 实验组

所有有缺陷的组从同一个 frozen RPent/Harness VLA artifact、初始 memory 和 failure traces 开始。

| 条件 | 可更新 plan/memory `P` | 可修改 skill `W` | 外部 gate | 作用 |
| --- | ---: | ---: | ---: | --- |
| Clean reference | 否 | 否 | 不适用 | 给出无缺陷性能上界，确认任务本身可解 |
| Frozen Harness | 否 | 否 | 不适用 | 论文配置锚点 |
| Plan/memory only | 是 | 否 | 不适用 | **Primary baseline**：Harness VLA 可用的最强非代码适应 |
| Code only | 否 | 是 | 是 | 判断代码 patch 是否独立有效 |
| Plan/memory + code | 是 | 是 | 是 | **Ours/full** |
| Full without gate | 是 | 是 | 否 | 验证 verifier 的因果贡献 |
| Human/oracle patch | 不适用 | 是 | 是 | 上界与 failure-type adjudication，不参与主要胜负 |

这近似一个 `Δmemory × Δcode` 的 2×2 设计，能估计 memory、code 和二者交互。primary comparison 是 `Plan/memory only` 对 `Plan/memory + code`；唯一新增能力是 `allow_code_edit`。

Direct frozen VLA 可在子集上保留为背景锚点，但它不是本论文最关键的比较对象；Harness VLA 已经证明它优于 direct VLA 的部分场景。

## Defect Benchmark 设计

### Controlled defects

第一轮用 deliberate defects，因为需要已知 root cause、clean reference 和 oracle patch。至少覆盖：

1. perception/geometry interface：坐标、深度有效性、frame/unit conversion；
2. primitive/contract：参数传递、gripper state、局部控制 contract；
3. monitor/postcondition：stale state、early return、false positive/negative；
4. exception/fallback/FSM：IK 或执行错误后的错误分支、状态转移缺失。

不能只做数字 threshold 调参，否则容易退化成参数搜索。正式集合需要同时包含参数错误、局部多行逻辑错误和跨函数 contract 错误；对纯参数 defect 应加入 random/grid/Bayesian parameter search 作为附加 baseline。

每个 defect 进入主集合前必须满足：

- 在独立 impact seeds 上，clean reference 成功率足够高、且 defect 相对 clean 造成预注册幅度的成功率下降；
- oracle plan/memory 不能稳定绕过；
- 隐藏 oracle patch 能恢复预注册比例的损失；
- public memory、prompt、文档和测试没有直接泄露修复；
- agent 看不到 clean commit、git history、issue/PR 或网络搜索。

pilot 可先用 `clean success >= 70%`、`defect impact >= 30 pp`、`oracle patch 恢复 >= 80% performance gap` 作为暂定 calibration criteria；这些数值只能在独立 pilot set 上调整一次，不能看过正式结果再改。

每个 mutant 应打包成没有父历史的新仓库快照；hidden tests 与 clean/oracle patch 位于 agent 无权限读取的 evaluator 环境。

### Negative controls

- plan/memory-repairable cases：检验代码系统是否不必要地 over-edit；
- policy-limited cases：检验是否正确 abstain；
- protected evaluator/safety case：检验 agent 是否试图 reward hack。

### Natural failures

在 deliberate-defect taxonomy 和实验门槛冻结之后，再加入少量真实 RPent failure 或历史 bug。它们只作为 external validity，不用于调整方法或主假设，避免用已知答案反复打磨系统。

## 数据划分与防泄漏

至少四层：

1. **Repair set**：每个 defect 只给 1–3 个 failure traces，供归因和生成 patch。
2. **Visible development tests**：skill contract 与少量 held-in case，agent 可直接看到。
3. **Hidden gate set**：回归、安全和扰动测试；只返回受限的聚合反馈，且限制 proposal 轮数。
4. **Final blind set**：新 seeds、位置、对象实例与任务；结果永远不返回 repair loop。

额外约束：

- defect adjudication、gate 和 final blind 使用不同 seeds；
- final task/seed split 在方法冻结前生成并密封；
- patch agent 禁止联网，不能读原仓库历史；
- evaluator、held-out tests、预算和 artifact hash 在独立权限域；
- 对相同 task/seed，各方法使用 paired execution；
- 任何 final blind 结果都不能用于重新选择 patch。

## 公平预算

必须分开报告两个预算：

### Adaptation budget

- 可见 failure traces 数；
- environment probes / test rollouts；
- patch 或 memory proposal 次数；
- repair-agent tokens、wall-clock 和 API cost；
- human intervention。

### Deployment budget

- execution planner turns/tokens；
- primitive 与 VLA call 数；
- environment steps；
- episode wall-clock；
- reset/retry 权限。

primary baseline 和 ours 的 deployment budget 必须完全相同。adaptation budget 尽量逐项封顶并匹配；如果无法把代码测试与 memory search 精确换算，必须报告 success–cost Pareto curve，不能只比最终成功率。

## 指标

对 defect `d` 定义：

```text
S_clean(d)  = clean code 在 final blind 上的成功率
S_bug(d)    = 有缺陷 fixed harness 的成功率
S_method(d) = 某方法适应后的成功率

normalized_recovery(d)
  = (S_method(d) - S_bug(d)) / (S_clean(d) - S_bug(d))
```

只有 `S_clean - S_bug` 超过预注册 impact threshold 的 defect 才进入主分析，防止分母接近零。

Primary metrics：

- held-out success 与 normalized recovery；
- safe-repair rate：目标收益达标、regression 合格且无 severe safety violation 的 defect 比例；
- 相对 plan/memory-only baseline 的 paired gain。

Secondary metrics：

- unaffected-task regression；
- safety violation、false acceptance 与 rollback；
- component attribution 与错误编辑率；
- patch/test proposal 次数；
- tokens、environment interactions、VLA calls、wall-clock 和成本；
- correct abstention 与 escalation rate。

## 统计分析原则

- **统计单位是 defect / failure family，不是帧，也不能把同一 patch 下的大量 seeds 当作完全独立样本。**
- task 与 environment seed 使用 paired runs。
- 主分析使用按 defect family 聚类的 bootstrap confidence interval，或 mixed-effects logistic model：

```text
success ~ method * failure_type
        + (1 | defect_family)
        + (1 | task)
        + (1 | environment_seed)
        + (1 | repair_agent_seed)
```

- regression 使用预注册的 5 pp non-inferiority margin；
- primary hypothesis 只有一个，secondary hypotheses 做 Holm/FDR correction；
- pilot 只估计方差和可行性，不与 confirmatory results 合并。

## 最小 Pilot

目标不是发论文，而是判断问题是否值得扩展：

- 4 个 code-repairable defects，覆盖 4 类组件；
- 1 个 plan/memory negative control；
- 1 个 policy-limited / abstention control；
- 4 个 LIBERO-Pro tasks；
- 每 case 2 条 repair traces；
- 每 case 5 个 final blind environment seeds；
- 3 个 repair-agent seeds；
- 先固定一个 execution planner 和一个 VLA checkpoint。

pilot 只需跑：

1. Plan/memory only；
2. Plan/memory + gated code；
3. Full without gate；
4. Clean/oracle reference。

暂定 Go 条件：

- 至少 3/4 code defects 在 final blind 上取得实质 normalized recovery；
- code 方法明显超过 plan/memory-only，而不是靠更多部署预算；
- plan negative control 不需要 code edit；
- policy-limited case 能正确 abstain；
- regression 不超过 5 pp；
- severe safety violation 为 0；
- 所有结果可由冻结 manifest 完整重放。

6 个 case 只能证明工程可行，不能支持论文级统计显著性。Confirmatory 阶段应使用完全独立的 tasks/defects，扩展到至少 12 个 code defects、多个 negative controls、10 个以上 held-out seeds 和多个 repair-agent seeds，再根据 pilot 方差做正式 power analysis。

一个可执行的 confirmatory 起点是：把至少 12 个 `task × defect` 单元分散到不同 LIBERO-Pro task family、扰动类型和上述 4 类组件；每个单元从空 agent context 做 3 次独立 repair run，每个冻结 patch 再评估 10 个 final-blind seeds。统计时先在单元内聚合 seeds 和 repair runs，再以 `task × defect` 单元为 cluster；不能把这些 episode 直接当成数百个独立样本。

主实验先固定一个 execution planner 与一个 repair-agent model，避免同时变化。方法和门槛冻结后，再在代表性 task/defect 子集上替换第二个 planner 和第二个 repair model，报告方向是否一致、成本变化与 failure-type interaction；这属于 robustness analysis，不与 primary endpoint 混合。

## 最容易导致拒稿的混淆

1. **多给了代码方法 rollout/token**：收益可能只是更多搜索。
2. **故意造只能由代码修的玩具 bug**：需要最小充分干预判定和自然 failure 外部验证。
3. **大量 seed 冒充大量独立样本**：真正的泛化单位是 defect family。
4. **Agent 看见 clean diff、issue 或 hidden tests**：会变成答案恢复，不是调试。
5. **改 evaluator、budget 或 safety threshold**：属于 reward hacking。
6. **只修数值参数**：可能被普通 optimizer 替代。
7. **只在触发 patch 的场景成功**：属于 trace overfitting。
8. **把 policy limitation 包装成 wrapper patch**：必须用有效 staging 和 policy oracle 做边界验证。
9. **第一篇就宣称 lifelong self-evolution**：先证明 verifier-guided local repair。

## 下一步产物

1. `experiment_manifest.yaml`：RPent/model/memory/planner/evaluator/budget 的版本与 hash。
2. `editable_surface.yaml`：`K/P/W` 的读写权限和禁止修改项。
3. `failure_taxonomy.yaml`：最小充分干预判定与 case 标签。
4. `trace_schema.yaml`：repair agent 实际能看见的证据。
5. `evaluation_protocol.md`：split、指标、margin、proposal 上限与统计方法。

只有这五项定下来，才应该开始实现 `code_evolving` mode；其工程里程碑继续由 [[研究切口与实验路线]] 维护。

## 为这套实验服务的阅读顺序

### Priority 0：先决定项目是否还有独立切口

1. [ASPIRE: Agentic /Skills Discovery for Robotics](https://arxiv.org/abs/2607.00272)：重点读 §2.1 execution engine、§2.2 skill library、§3.3 evaluation protocol 和 §5 limitations；它是当前最直接的 novelty threat。
2. [VASO: Formally Verifiable Self-Evolving Skills for Physical AI Agents](https://arxiv.org/abs/2606.05395)：重点读 §3 skill formalization、verification/counterexample update loop 和 §7 limitations；它决定我们能否只说“verifier-guided”，还是必须明确“shared implementation repair + empirical Robot CI”。

### Priority 1：直接改变假设与实验

3. [HELM](https://arxiv.org/abs/2604.18791)：memory、state verifier、rollback/replanning 与 LIBERO-Recovery；先用它构造最强非代码恢复 baseline 和 controlled perturbation protocol。
4. [DebugRepair](https://arxiv.org/abs/2604.19305)：中间 runtime evidence、自主 instrumentation 和 test purification，直接支撑 H5 的 trace ablation。
5. [SAFE](https://arxiv.org/abs/2506.09937)：跨任务 VLA failure detector 与 conformal calibration；用于把“何时触发 repair”从启发式判断变成可测 monitor。
6. [STING](https://arxiv.org/abs/2604.01518)：说明弱 regression suite 会接受语义错误 patch；用于设计 mutation-guided hidden tests 和 false-acceptance 指标。
7. [vla-eval](https://arxiv.org/abs/2603.13966)：统一模型/benchmark 隔离、协议复现与并行评测；用于冻结 evaluator artifact 和扩大 held-out evaluation。

### Priority 2：理解边界与替代路线

8. [InSight](https://arxiv.org/abs/2606.24884)：当失败确实需要新低层 primitive 时，data flywheel 和 VLA skill acquisition 是 code repair 的替代路线。
9. [RepairAgent](https://arxiv.org/abs/2403.17134)：工具调用、信息收集、候选 patch 验证和成本报告，是 repair-agent workflow 的软件工程锚点。
10. [RoboCritics](https://arxiv.org/abs/2603.06842)：motion-level expert critics、人类可读安全反馈与修复，适合设计真实机器人阶段的独立 safety critic。
