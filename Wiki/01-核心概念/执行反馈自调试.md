# 执行反馈自调试

核心判断：执行反馈自调试是本项目的核心机制，但 ASPIRE 已证明宽泛的“机器人 trace → program repair”闭环；当前研究问题必须进一步限定为 frozen VLA harness 中共享 implementation 的受验证修复与干预路由。

## 闭环定义

执行反馈自调试可以写成：

```text
skill 执行
  -> 失败检测
  -> 收集多模态 trace
  -> 失败归因
  -> 生成 patch proposal
  -> 仿真与回归测试
  -> 安全部署或回滚
```

这个循环和传统训练不同。传统路线常常是收集更多轨迹、重新训练或微调模型。本项目优先问：

> 这次失败是否可以通过更好的前置条件、参数、几何计算、fallback、检测器或错误处理来修复？

如果答案是可以，代码修复可能比重新训练更快、更便宜、更可解释。

## 失败归因

机器人失败不是一个单点事件。抓取失败可能来自：

- 感知错误：物体检测框偏移、深度图空洞、pose estimation 置信度低。
- 世界模型错误：场景图没有更新、物体被遮挡、可达性判断错误。
- 规划错误：IK 到达关节边界、路径碰撞、目标姿态不可执行。
- 控制错误：力控阈值不合适、末端轨迹跟踪偏差、gripper 闭合策略错误。
- 执行扰动：物体滑动、桌面摩擦异常、杯子透明或反光。
- 验证错误：skill-local postcondition/monitor 写得太宽或太窄，或者只读外部 evaluator 本身异常；两者必须分开归因。
- 任务分解错误：高层 planner 在 precondition 不满足时调用了 skill。

因此，coding agent 不应该直接“改代码试试看”。它应该先给出 failure attribution，再提出最小 patch。

## 从失败检测到干预路由

failure detector 只能回答“可能失败了”，不能直接回答“应该改哪里”。[SAFE](https://arxiv.org/abs/2506.09937) 表明可以从 VLA latent features 学习跨任务 failure score，并用 conformal prediction 校准检测阈值；这适合充当 repair trigger，但不能替代 root-cause attribution。

本项目还必须按“最小充分干预”决定处理路径：

- plan/memory-repairable：固定代码，只做重绑定、staging、顺序或 retry；
- code-repairable：前一路径仍失败，但受限 skill implementation patch 能恢复；
- policy-limited：只有采集数据、微调或替换低层 policy 才能恢复；
- trusted-kernel/out-of-scope：evaluator、传感器、硬件或任务可行性异常，应 abstain 和上报。

这个路由避免 coding agent 把每次失败都解释成代码 bug。预注册判定顺序与反事实 oracle 见 [[问题定义与实验假设]]。

## 三层可观测归因

[[Harness Engineering for Self-Improvement - 综述解读|Harness Engineering for Self-Improvement]] 汇总的 Self-Harness 与 Agentic Harness Engineering 提醒我们，终局错误码不足以决定修改位置。每次失败至少要区分：

1. **Terminal cause**：verifier 最终看到什么，例如 timeout、missing artifact、goal predicate false。
2. **Causal behavior**：机器人或 agent 做了什么导致终局失败，例如选择了错误目标、空抓后仍继续 transport。
3. **Exposed mechanism**：哪个 harness 组件需要修改，例如 grounding prompt、skill implementation、postcondition 或 memory rule。

对应的 trace 分析流程应是：

```text
原始多模态 rollout
  -> 单次任务因果报告
  -> 跨 seed / 跨任务失败模式
  -> 映射到明确组件
  -> 带预测与回归风险的最小 patch
```

这也是 component observability 的要求：planner、tool description、skill、middleware、monitor 和 memory policy 都要有独立版本，才能知道改动发生在哪里。

## Trace 应该包含什么

一个可调试 trace 至少包含：

```yaml
task_id: clean_kitchen_trial_023
skill: grasp_mug
skill_version: v0.3.1
goal: 抓起桌面左侧白色杯子
pre_state:
  object_pose: ...
  depth_confidence: ...
  scene_graph: ...
execution:
  selected_grasp_point: ...
  planned_trajectory: ...
  actual_ee_trajectory: ...
  force_torque: ...
  planner_status: ...
post_state:
  object_in_gripper: false
  object_displacement: 0.18m
failure_label: grasp_slip_or_pose_error
artifacts:
  rgb_before: path/to/image
  depth_before: path/to/depth
  video_clip: path/to/video
```

这份 trace 是机器人世界里的“测试失败日志”。没有它，就很难把 [[自进化代码Agent与评估器]] 的经验迁移到机器人。

## Patch proposal 的标准格式

好的 patch 不只是代码差异，还要包含假设和验证方式：

```text
Hypothesis:
  杯柄区域深度无效，导致 3D 抓取点偏到杯子后方。

Patch:
  1. 对候选抓取点周围做 depth validity filtering。
  2. 若有效深度比例低于阈值，切换到杯身抓取。
  3. 在抓取前加入小幅换视角动作。

New tests:
  - handle_depth_holes
  - handle_occluded_body_fallback
  - valid_handle_still_preferred

Deployment risk:
  可能降低杯柄抓取优先级，需要在透明杯和普通杯上分别回归。
```

## 和相关工作的关系

- [[voyager-2305.16291.pdf|Voyager]] 证明了可执行代码 skill library 可以在环境反馈中增长，但它发生在 Minecraft。
- [[alphaevolve-2506.13131.pdf|AlphaEvolve]] 证明了 coding agent 需要 evaluator 才能可靠进化代码。
- [[code-as-policies-2209.07753.pdf|Code as Policies]] 证明了 LLM 可以生成机器人 policy code，但本项目更强调失败后的长期维护。
- [[Harness VLA]] 证明冻结 VLA 可以作为可重试 primitive，失败后通过重新 staging、观察和再次调用来局部恢复；但它不修改 skill 实现。
- [ASPIRE](https://arxiv.org/abs/2607.00272) 已经用 per-primitive multimodal traces 支持 robot program 的失败诊断、修复与验证，因此“收集 trace 后让 agent 修程序”本身不再足以构成新意；本项目需聚焦跨任务共享 implementation 与 hidden regression。
- [DebugRepair](https://arxiv.org/abs/2604.19305) 表明 intermediate runtime evidence、自主 instrumentation 与 purified failing context 能改善软件 repair；它直接支持比较 terminal-only、固定 structured trace 与 agent-requested probe。
- [[Harness Engineering for Self-Improvement - 综述解读|Harness Engineering for Self-Improvement]] 将失败驱动修改扩展到整个 harness，并强调 verifier-grounded evidence、受限编辑面和 held-out 回归。
- [Lifelong Robot Library Learning](https://arxiv.org/abs/2406.18746) 已经把“skill library 增长”带到机器人语境，本项目可以进一步强调 execution failure repair。

## 边界

执行反馈自调试最适合修复：

- 坐标变换、阈值、fallback、异常处理。
- precondition/postcondition 写错。
- 使用 perception API 的方式不稳。
- 调用顺序或状态机转移错误。
- regression tests 缺失。

它不擅长直接解决：

- 灵巧手复杂接触控制。
- 布料、液体、柔性物体操作。
- 视觉模型根本没有识别能力的问题。
- 硬件设计或传感器缺陷。

遇到这些情况，coding agent 应该提出“需要训练 learned policy / 收集数据 / 更换传感器 / 改末端执行器”，而不是假装几行代码能解决。
