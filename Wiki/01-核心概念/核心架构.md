# 核心架构

核心判断：系统应该被设计成“高层智能 + 可验证技能层 + 安全执行层 + 自调试维护层”，而不是让一个 LLM 直接控制机器人。

## 七层结构

### 1. 任务大脑

任务大脑接收自然语言指令、图像/场景状态、机器人状态和可用 skill 列表。它输出的是计划，而不是电机控制。

例如：

```text
clean_kitchen:
  detect_dirty_objects()
  for each cup on table:
    grasp_object(cup)
    place_object(cup, sink)
  wipe_table(table)
  verify_cleanliness(kitchen)
```

这里可以借鉴 [[LLM规划与代码生成]] 中的 SayCan、Inner Monologue、ProgPrompt。任务大脑的关键约束是：它只能调用 registry 中存在、且 precondition 被满足的 skill。

### 2. Skill Registry

每个 skill 不只是一个函数，而是一份可维护的软件资产：

```yaml
name: grasp_mug
description: 抓取杯子，优先使用杯柄；若杯柄不可见则回退到杯身抓取。
inputs:
  object_id: string
  grasp_preference: handle | body | auto
outputs:
  success: boolean
preconditions:
  - object_visible(object_id)
  - object_pose_confidence >= threshold
  - reachable(object_pose)
postconditions:
  - object_in_gripper(object_id)
safety_constraints:
  - no_collision
  - joint_limits_satisfied
  - force_below_limit
known_failure_modes:
  - transparent_object_depth_holes
  - handle_occluded
  - pose_estimation_low_confidence
tests:
  - sim_mug_handle_visible
  - sim_mug_handle_occluded
  - sim_transparent_mug_depth_invalid
```

这个 registry 是 coding agent 的工作边界：agent 可以改实现、参数、fallback、检测条件和测试，但不能绕过安全约束直接发危险动作。

### 3. 感知与世界状态层

这一层把传感器转成可用状态，包括 RGB、深度、点云、物体检测、语义分割、6D pose、场景图、可达性和碰撞几何。

用户原始想法里“杯柄像素 + 深度图像素 -> 三维位置”就在这里。它不是高层 LLM 该直接处理的细节，而是 skill implementation 和 perception API 的交界。

### 4. Skill Executor

执行器应以传统机器人控制和 learned policy 的混合方式实现：

- 运动规划：MoveIt、OMPL、IK、碰撞检测。
- 控制：轨迹跟踪、力控、阻抗控制、限速限力。
- 学习策略：Diffusion Policy、ACT、OpenVLA、pi0 等可以作为某些 skill 的实现。

重要原则是：LLM 不做高频闭环控制。LLM 负责生成或修改可检查的软件结构，低层实时控制由可靠执行器承担。

### 5. Execution Monitor

monitor 负责把“失败”变成可诊断 evidence。对于抓杯子失败，它至少应记录：

- 任务目标和调用的 skill 版本。
- 执行前后的图像、深度、点云或视频片段。
- 目标物体 pose、置信度、抓取点和抓取姿态。
- 计划轨迹与实际末端轨迹。
- gripper force、关节状态、碰撞事件和 planner error code。
- success detector 的输出和理由。

没有高质量 trace，coding agent 只能猜。

### 6. Coding Agent / Skill Repair Agent

coding agent 的输入是失败 trace、skill 代码、registry 元数据、API 文档、历史版本和测试结果。它输出的是 patch proposal，而不是直接部署。

一个理想 patch proposal 包含：

- 失败假设：例如“杯柄区域深度无效，导致 3D grasp point 偏移”。
- 代码修改：例如加入 depth validity filtering 和 body-grasp fallback。
- 新测试：例如 `test_transparent_mug_depth_holes`。
- 风险说明：例如可能降低杯柄优先抓取率。

这里对应 [[执行反馈自调试]] 和 [[自进化代码Agent与评估器]]。

### 7. Verifier / Deployment Gate

验证门决定 patch 能不能进 skill library。它至少包括：

1. 静态检查和类型检查。
2. 单元测试和 API contract 测试。
3. 仿真测试和扰动测试。
4. 旧任务回归测试。
5. 安全约束检查。
6. 小范围真实机器人测试。
7. 版本化发布和失败回滚。

这个部分是 [[Robot CI-CD与安全门]] 的核心。

## 关键设计取舍

系统不应该把所有能力都写成规则代码。更合理的边界是：

- 可归因、可测试、可符号化的失败，优先交给 coding agent 修复。
- 接触丰富、连续控制、触觉复杂、难以手写的动作，优先使用 learned policy。
- 高风险动作必须通过 DSL、安全约束和 runtime monitor。

因此，最终系统应是混合式：

> LLM/VLM 规划 + 可验证 skill code + 传统控制 + learned policy + coding agent 自调试。
