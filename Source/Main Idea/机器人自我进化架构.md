## 3\. 这个方向最大的价值在哪里

我觉得它有三个很强的价值点。

第一，它比端到端 VLA **更可解释** 。VLA 失败时，你可能只知道“模型没学会”；但你的系统失败时，可以定位到是深度估计、坐标转换、抓取点选择、IK、碰撞检测、力控阈值、状态机转移，还是 success detector 出了问题。

第二，它比纯传统机器人系统 **更灵活** 。传统机器人 stack 通常靠人类工程师调参、写规则、加 fallback。你的想法是让 coding agent 承担一部分工程师工作：看日志、看图像、看异常、改代码、跑测试、写新 skill。

第三，它比“重新训练一个大模型” **更样本高效** 。对于很多失败，根本不需要收几千条数据重新训练；可能只是一个坐标系变换错了、抓取姿态没考虑杯柄、深度图 invalid pixel 没处理、关节限位检查漏了、precondition 太宽。代码修复能比神经网络微调快很多。

但它也有一个核心限制： **它更擅长修复“可符号化、可测试、可归因”的失败，不擅长凭空学会复杂连续控制。**

比如：

“杯柄检测失败”“抓取点应该偏移 2cm”“透明杯深度无效要换视觉策略”“柜门把手需要先估计朝向”，这些适合 coding agent。

但“灵巧手如何用触觉稳定旋转杯子”“柔性布料如何折叠”“接触动力学很复杂的插拔任务”，这些很难只靠改代码解决，通常还需要 imitation learning、RL、diffusion policy、VLA 或专门的低层控制学习。

## 4\. 它能不能代替 VLA？

我的看法： **短期不能完全代替 VLA，但可以成为比 VLA 更实用的上层/旁路系统。**

VLA 的优势是：它能从大量机器人轨迹里学到很多“人类很难手写”的动作细节。比如 π0 这类模型的目标就是通过大规模、多机器人数据训练一个 generalist robot policy，能在多种平台上执行洗衣、擦桌、组装等任务。OpenVLA、Octo、SmolVLA 等开源路线也都在降低 VLA 训练和部署门槛。 [^8]

你的路线的优势是：它不需要所有能力都从数据中学。它可以把已知可靠的机器人学模块复用起来，比如 SLAM、pose estimation、grasp planning、MoveIt/OMPL、behavior tree、force control、视觉检测器、VLM 等。TAMP 本身就是把高层任务规划和低层运动规划结合起来，应对长时序、动态、复杂机器人任务；OMPL/MoveIt/ROS 这类基础设施也已经长期服务于传统机器人系统。 [^9]

所以更好的说法不是：

> 用 coding agent 代替 VLA。

而是：

> 用 coding agent 给机器人建立一个可解释、可测试、可持续进化的 skill 层；VLA 可以作为其中某些 skill 的实现方式，也可以作为 fallback 或低层 policy。

也就是说，未来最有希望的系统很可能是混合式：

> LLM/VLM 规划 + 可验证 skill code + 传统控制 + learned policy / VLA + coding agent 自调试

## 5\. 真正有论文价值的新颖点

这个项目如果要变成强科研项目，不能只说“让 LLM 写机器人代码”。这个已经有人做了。真正要强调的是下面这些点。

### 新颖点一：机器人 skill 的“执行后自调试”

现有 Code as Policies 更像是“根据语言生成 policy code”。你的系统应该强调：

> 机器人执行失败以后，系统根据物理执行 trace 自动诊断并修复 skill。

这个 trace 不只是报错日志，还应该包括：

图像、深度图、分割 mask、3D 点云、末端位姿、关节状态、力/扭矩、碰撞信息、规划器返回码、success detector 结果、任务前后状态变化、视频片段。

这会让它区别于普通 coding agent，因为普通代码测试只需要 unit test，而机器人调试需要 **多模态、物理世界、时序因果** 。

### 新颖点二：Skill 代码不是自由 Python，而是受约束的机器人 DSL

如果你让 LLM 随便改 Python 控制机器人，风险非常大。更好的研究设计是定义一个类似 Robot Skill Language / Skill DSL 的中间层。

比如每个 skill 都有：

```
skill: grasp_mug
inputs: object_id, grasp_preference
preconditions:
  - object_visible(object_id)
  - object_pose_confidence > threshold
  - robot_reachable(object_pose)
postconditions:
  - object_in_gripper(object_id)
safety_constraints:
  - max_force < F
  - no_collision
  - joint_limits_satisfied
implementation:
  - perception_query
  - grasp_candidate_generation
  - motion_plan
  - guarded_execute
  - verify_grasp
```

coding agent 可以改的是 skill 内部逻辑、参数、fallback、检测条件、调用顺序，而不是直接绕过安全层发电机命令。NRTrans 这类工作已经说明，“机器人 skill language + compiler/debugger + feedback”是很重要的方向。 [^7]

### 新颖点三：Robot CI/CD

这可能是你项目最强的概念。

每次 coding agent 修改 skill，都必须经历：

1. 静态检查
2. 类型检查 / API 检查
3. 仿真测试
4. 回归测试
5. 安全约束验证
6. 小范围真实机器人测试
7. 版本化发布
8. 失败后自动回滚

这就把机器人 skill 变成软件工程里的可测试模块。AlphaEvolve 的成功关键也是有 evaluator：LLM 生成代码，系统用自动评估器判断改动是否真的更好。你的机器人系统也必须有 evaluator，否则 coding agent 会变成“看起来会改，但不知道有没有真的变好”。 [^10]

### 新颖点四：失败归因

机器人失败不是只有“代码错了”。可能是：

感知错、世界模型错、规划器错、执行器打滑、物体透明、遮挡、抓取点不稳定、物体超出可达空间、指令本身模糊、skill precondition 不满足、success detector 错判。

所以一个强论文应该不只是“LLM 改代码”，而是做一个 **failure attribution module** ：

> 先判断失败属于 perception / planning / control / execution / verification / task decomposition 哪一类，再让 coding agent 修改对应模块。

这会比简单 retry 强很多。

## 6\. 推荐系统架构

我会把你的系统设计成 7 层。

### 第一层：任务大脑

输入：

自然语言指令、当前图像、场景图、机器人状态、skill registry。

输出：

一个 behavior tree / task graph / PDDL-like plan。

例如：

```
clean_kitchen:
  1. detect_dirty_objects()
  2. for each cup on table:
       grasp_mug(cup)
       place_in_sink(cup)
  3. wipe_table()
  4. verify_kitchen_clean()
```

SayCan、Inner Monologue、ProgPrompt 都能作为这一层的参考。 [^2]

### 第二层：Skill Registry

每个 skill 不只是代码文件，而是一整套元数据：

```
name
description
input schema
output schema
preconditions
postconditions
safety constraints
dependencies
known failure modes
test cases
simulation scenes
hardware compatibility
version history
```

这一步非常关键，因为 coding agent 需要知道“它可以改什么、不可以改什么”。

### 第三层：感知与世界状态层

这层负责把传感器转成可用状态：

RGB、深度、点云、物体检测、6D pose、语义分割、抓取候选、场景图、可达性、碰撞几何。

你提到“杯柄在图像上的像素 + 深度图像素 → 三维位置”，这个就属于这一层和 skill code 的交界。

### 第四层：Skill Executor

执行层不应该是 LLM。它应该是传统机器人控制系统和 learned policy 的组合：

MoveIt / OMPL 做运动规划，IK solver 做逆解，force controller 做接触控制，VLA / diffusion policy 可以作为某些复杂动作的低层实现。

这样做的好处是：低层动作稳定、安全、实时；LLM 不需要 50Hz 控制机器人。

### 第五层：Execution Monitor

这个模块负责记录失败证据。

比如 grasp\_mug 失败，monitor 应该记录：

```
object pose before grasp
selected grasp point
planned trajectory
actual end-effector trajectory
depth confidence
gripper force
object moved or not
collision events
success detector output
video clip
planner error code
```

没有这个模块，coding agent 只能猜。

### 第六层：Coding Agent / Skill Repair Agent

它的输入是：

失败 trace、skill 代码、相关文档、API 说明、历史版本、测试结果、类似失败案例。

它的输出不是直接部署的代码，而是一个 patch proposal：

```
hypothesis:
  failure caused by invalid depth around mug handle

patch:
  add depth validity filtering
  fallback to cup body grasp if handle depth confidence < threshold
  add viewpoint adjustment before grasp

tests:
  test_mug_handle_occluded
  test_transparent_mug_depth_holes
  test_sideways_mug
```

这和 Self-Debugging、AlphaEvolve、Voyager 的精神很接近：根据执行反馈修改代码，而不是靠一次性生成。 [^11]

### 第七层：Verifier + Deployment Gate

这个模块决定 patch 能不能进 skill 库。

它要看：

是否通过 unit test；  
是否通过仿真测试；  
是否引入安全违规；  
是否让旧任务退化；  
真实机器人小样本测试是否成功；  
是否需要人类批准。

没有这个 gate，系统就不安全。

## 7\. 最小可行研究版本怎么做

不要一上来做人形机器人清理厨房。太难。

我建议从一个桌面机械臂开始，比如 Franka、UR5、xArm、ALOHA、LeRobot 机械臂，做 5 到 10 个可控 manipulation skill。

### 第一阶段：仿真 proof-of-concept

环境可以选 LIBERO、CALVIN、RoboCasa、BEHAVIOR-1K 或 ManiSkill/RoboSuite 类平台。LIBERO 专门做 lifelong robot learning，有 130 个任务；CALVIN 面向长时序语言条件操作；RoboCasa 聚焦厨房环境，包含大量日常任务；BEHAVIOR-1K 有 1000 个日常活动和复杂物理模拟。 [^12]

你可以故意设计一些初始有缺陷的 skill：

抓杯子不处理透明物体；  
抓杯柄时坐标系转换有 bug；  
开抽屉时 force threshold 太低；  
擦桌子时覆盖区域计算错误；  
放物体时没有检测容器边界；  
深度图 invalid pixel 没处理。

然后看 coding agent 能否根据失败 trace 自动修复。

### 第二阶段：真实机械臂

选 3 到 5 个真实任务：

抓杯子；  
按杯柄或杯身选择抓取方式；  
把杯子放进水槽/盒子；  
打开抽屉；  
擦桌子；  
整理桌面物品。

对比 baseline：

静态 skill library；  
LLM planner + 静态 skill；  
Code as Policies 式一次性生成；  
你的 code-evolving skill library；  
可选：OpenVLA / diffusion policy / ACT baseline。

ALOHA/ACT 这类工作说明低成本双臂平台和 action chunking 能在细粒度操作上取得很强表现，也适合作为你系统里的 learned skill 或对比基线。 [^13]

### 第三阶段：lifelong / regression benchmark

真正的亮点应该是：

> 机器人在任务 A 上修好了 skill，不应该把任务 B、C、D 弄坏。

所以你要测：

修复成功率；  
平均多少次 trial 修好；  
修复后泛化到新物体/新位置/新光照的能力；  
旧任务 regression rate；  
安全违规次数；  
人类工程师介入时间；  
与重新训练 VLA / policy 相比的数据效率。

## 8\. 它的最大技术挑战

### 挑战一：失败原因很难自动判断

机器人失败经常是链式的。

比如“抓杯子失败”可能是：

物体检测框偏了 → pose estimation 错了 → IK 找到了边界解 → 轨迹擦到杯子 → 杯子倒了 → success detector 判断失败。

coding agent 如果只看到最后结果，可能会改错地方。因此你需要一个强大的 trace system 和 failure classifier。

### 挑战二：仿真测试不等于真实世界

coding agent 在仿真里修好了，不代表真实机器人能跑。尤其是摩擦、柔性物体、透明/反光物体、接触力、相机噪声、标定误差，都是 sim-to-real 的大坑。RoboCasa、BEHAVIOR-1K 这类 benchmark 正在努力提高家庭任务仿真的真实性，但长时序复杂操作仍然是机器人学习的难点。 [^14]

### 挑战三：LLM 写代码会引入 regression

它可能修好了杯子，却搞坏了碗；修好了正面抓取，却搞坏了侧面抓取。这就是为什么必须有 skill-level regression tests。

### 挑战四：真实机器人不能让 agent 随便试错

在 Minecraft 里失败只是游戏角色死了；在真实机器人里失败可能撞坏手、砸坏杯子、夹到人、烧电机。因此真实系统必须采用：

仿真优先；  
安全沙箱；  
限制动作空间；  
runtime monitor；  
force/velocity/torque limits；  
human approval；  
自动回滚。

### 挑战五：很多能力不是“改代码”能解决的

如果一个 skill 失败是因为视觉模型根本识别不了透明玻璃，coding agent 加几行规则可能不够。它可能需要：

换传感器；  
换视角；  
调用更强 VLM；  
收集数据微调 perception model；  
训练一个 learned policy；  
改硬件末端执行器。

所以你这个系统最好支持“skill = code + model + data + tests”，而不是狭义的纯代码。

## 9\. 我对它的总体评价

我觉得这个项目 **有研究潜力，而且方向很聪明** ，但要换一个更准确的叙事。

不建议说：

> 我要用 coding agent 解决通用机器人 AGI，替代 VLA。

建议说：

> 当前 VLA 虽然强，但黑箱、数据饥渴、失败难调试。我们提出一种 code-evolving robotic skill framework，让机器人通过执行失败反馈自动修复可解释 skill code，并用仿真、形式化约束和回归测试保证安全部署。

这个叙事更像一篇强论文。

### 顶会潜力判断

**ICRA / IROS：很有机会。**  
如果你能在真实机械臂上展示多个 skill 的自动修复、成功率提升、低人类干预和安全验证，这会很适合机器人会议。

**CoRL / RSS：有机会，但要求更高。**  
需要证明这不是工程拼装，而是提出了新的学习/自改进框架，并且在真实机器人或高质量 benchmark 上显著优于 baseline。

**NeurIPS / ICLR：也有机会，但要更抽象。**  
需要把它形式化成“embodied program repair”“test-time skill evolution”“agentic policy improvement via executable code”，并提供可复现 benchmark、大规模实验和理论/系统贡献。

## 10\. 最好的研究切口

我建议你把第一篇论文聚焦成这个题目：

> **Self-Debugging Robot Skills: Execution-Feedback Program Repair for Embodied Manipulation**

核心问题：

> 给定一个失败的机器人 skill、执行 trace 和任务目标，LLM coding agent 能否自动提出安全 patch，使机器人在相似和变化场景中成功率提高，同时不破坏旧 skill？

这个问题足够具体，能做实验，也有新意。

论文贡献可以写成：

1. 一个机器人 skill DSL / skill registry；
2. 一个多模态 execution trace 格式；
3. 一个 failure diagnosis + code repair agent；
4. 一个 simulation-to-hardware verification pipeline；
5. 一个 benchmark：故意设计多类机器人 skill failure；
6. 真实机器人实验：证明系统能减少人类调试成本，提高任务成功率。

## 11\. 最终判断

这个想法 **不是空想** 。它站在几个趋势的交点上：

VLA 正在快速发展；  
LLM 已经能写机器人 policy code；  
Voyager/AlphaEvolve 证明“代码 + evaluator + 反馈循环”很强；  
机器人系统本来就是模块化软件；  
真实机器人最缺的不是单次 demo，而是持续调试、泛化和安全部署。

但它的关键不是“让 coding agent 直接产生智能”，而是：

> **把机器人学习的一部分，从神经网络参数更新，转化为可解释软件系统的持续修复。**

这会是一个很有价值的研究方向。我的建议是：\*\*把它定义成“机器人 skill 的自调试与自进化框架”，而不是“新型 AGI 架构”。\*\*这样既更科学，也更容易做出可验证成果。
